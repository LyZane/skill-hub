# 订单清洗与仓库销量核对

将平台导出的订单明细变为可追溯的仓库对账工作簿。这里的“销量”表示订单中有物流信息的出库件数；“退货”表示其中申请退款的件数，不表示仓库已签收入库。保留补单与真实订单的分区，以及退货与真实订单的包含关系。

使用当前环境可用的表格读取、编辑、公式计算与渲染能力；已有表格处理规范时遵守其工具与格式要求。不要假设操作系统、客户端、文件位置、月份、店铺、SKU 映射或上一次会话的数据。

## 开始时引导用户

先检查用户已经提供的信息和可访问文件，再简短说明：

> 我会保留全量订单，按你提供的补单号分成真实订单和补单订单，再按商家编码统计有物流的出库件数及其中申请退款的件数，另列退货订单供仓库核对。退货数量不代表仓库已收货。

每次任务需要：订单明细文件、补单订单号（或明确本次无补单）、必要的编码合并规则。已提供或已确认的信息不重复问；先做文件检查、状态枚举等不依赖回答的工作。缺失信息尽早集中询问，避免逐条盘问。

- 首次使用，说明下文默认口径，并请用户确认或调整；已明确认可该口径的会话直接执行。
- 未提供补单号时，询问“请提供本次补单订单号，或说明本次无补单”。不把未提供自动解释为没有补单。
- 不确定来源工作表、业务状态或 SKU 含义时，给出候选项、记录数量和建议。只有影响业务结果的决定需要确认。
- 用户若只要分析、预览或流程说明，不擅自改文件。用户明确要求处理并保存时，常规操作直接完成。

## 输入检查与字段

识别表头和实际数据区域，读取完整字段，不能只抽样后直接统计。

| 字段 | 用途与检查 |
|---|---|
| 商家编码 | SKU 主键；作为文本保留大小写、连字符、前导零 |
| 购买数量 | 累计件数；不能用记录条数代替 |
| 子订单编号、主订单编号 | 补单号同时匹配两列；至少需要一个可靠订单编号字段 |
| 物流单号、物流公司 | 任一非空代表出库；缺少整列不能直接视作所有值为空 |
| 退款状态 | 判断退款申请；不能仅靠订单状态或退款金额推断 |
| 商品标题、商品属性 | 识别非实物、辅助核对；无法识别非实物时向用户补充询问 |
| 订单状态、退款金额、发货时间 | 辅助解释异常；不取代物流和退款状态的口径 |

字段别名应按语义映射并记录；关键列缺失或存在多个可能映射时先澄清。保留源字段名称和所有原始列。确认每行代表子订单商品明细，而非总计、分页重复表头或仓库拆包明细。

订单号在全过程中使用精确文本，不转浮点数。输入列表可以自动清理空行、两端空格、列表序号和完全重复号码，报告去重数量。表格中超长数字单元格可能已经丢失精度，科学计数法只是显示问题与真实精度损失须区分；不能通过补零猜测恢复，发现损失要求原始文本导出或可靠来源。

数量可将严格数值文本转换为数值；空白、负数、非数值、商品件数的异常小数须核对。不能默认填 1、默认为 0 或截断小数。重复子订单明细不自动删除，先排查重复导出、拆分发货或不同商品行。

判断空白时可以忽略两端空格；“-”“无物流”“暂无”等非空占位文本不应默默当成真实物流，需要提示核对。零、缺失、未知分别处理。

## 保留全量与统一编码

1. 新文件识别可靠的原始全量订单 sheet，重命名为“全量订单”。保留全部记录；编码标准化不等于删改订单数量、状态或其他字段。
2. 应用用户已确认的编码映射，报告每组映射涉及的记录数。新发现的相似名称仅建议合并，不因相似、大小写或型号推断就改码。
3. 编码映射优先来自本次输入或已确认的会话规则。不内置某家店的映射，不把示例当通用规则。遇到映射链、循环或互相冲突先明确最终目标，避免次序影响结果。
4. 全量订单及其派生表保持统一后的商家编码一致；在统计页的说明区记录生效映射。修改源文件前保留可恢复的原版，或使用用户指定的新输出文件。

已有输出时先执行 [重复运行与异常处理](references/edge-cases.md#重复运行)，不能将已经剔除补单的表误当全量，也不能未经说明覆盖用户另加的仓库核对信息。

## 分拣订单：全量保留、两表互斥

对每条全量订单记录，将输入补单号与子订单编号、主订单编号精确匹配，任一匹配即归入补单订单。同一行即使两列同时匹配也只分配一次。

- **全量订单**：全部标准化记录，保留原有顺序。
- **真实订单**：未匹配补单号的记录。
- **补单订单**：匹配补单号的记录。
- 确认无补单时，补单订单保留表头，真实订单包含全量记录。
- 一个主订单号可匹配多条商品明细，应全部分拣并解释“号码数”与“记录数”不同。
- 未匹配号码单独报告；继续处理已匹配部分，提醒未匹配号码未影响本次分拣，必要时待补充来源后重跑。

复制完整行与表头并保留格式，不只保留统计列。派生表可维持全量中的相对行序，无需按输入号码顺序重排。其他无关 sheet 不变。

## 实物识别、出库与退货

只对“真实订单”运行业务判断。先排除非实物，再判断出库，再判断退货。所有订单仍保留在相应明细表中。

### 非实物

明确的运费、补差价、差价支付、非实物咨询等不计任何销量或退货，也不进入退货订单。综合编码、标题与商品属性识别，不能因为标题含“包邮”“运费险”“补发”等词就排除正常商品。

滤网、配件、赠送但实际出库的实物不能仅因不是主机而排除；用户另有范围要求时遵循并注明。疑似非实物但不能确定的记录列出供用户判定，不默默删除。

### 默认统计口径

| 指标 | 规则 |
|---|---|
| 出库销量 | 实物，物流单号或物流公司至少一项有效非空，累计购买数量 |
| 未出库 | 两项物流信息均为空，不计销量；即使有发货时间也不算 |
| 退货量 | 实物、已出库，并且退款状态表示有退款申请，累计确认的退货件数 |
| 净销量 | 出库销量减退货量 |

默认处理真实订单全部记录，不另按下单、付款或发货月份过滤。文件名含“8 月”不能自动排除跨月行；发现跨月时说明，用户要按日历月份核对再明确日期字段和范围。

先枚举实际退款状态及频数，再建立状态映射：

- `没有申请退款`、明确无申请状态：不计退货。
- `退款成功`：已出库的实物通常计退货；未出库不计。
- `卖家已经同意退款，等待买家退货`：已出库即计退货，包括订单状态仍为 `卖家已发货，等待买家确认` 的情形。不要要求交易关闭、退款成功或仓库签收。
- 其他明确处于退款申请/退货处理中的状态按同一申请口径纳入，并向用户展示映射。
- 空白、未知状态、已撤销、被拒绝、申请关闭、仅退款不退货、部分退款，参考 [退款与数量例外](references/edge-cases.md#退款与数量例外)；不能用“不是没有申请退款”一条规则把所有异常状态无差别计入。

当一行购买多件但只退部分、退款可能只是差价、或有明确不退货的信息，不能凭金额比例推算退货件数，也不能把整行购买数量自动作为实际退回数量。询问采用申请口径整行统计还是确认退货件数，记录依据。待确认部分不输出无保留的精确净销量。

实物已出库但缺商家编码时，列为“未填商家编码（待核对）”，并保留来源行和订单号。已知 SKU 合计与待核对实物分列，不能直接丢弃造成漏算。

## 输出五个 sheet

| Sheet | 内容 |
|---|---|
| 全量订单 | 全部记录，统一后的编码，用于追溯 |
| 真实订单 | 排除补单后的完整记录；包含退货记录 |
| 补单订单 | 匹配的完整订单记录 |
| 退货订单 | 真实订单中符合退货条件的完整实物记录副本 |
| 统计 | 按商家编码汇总出库销量、退货量、净销量、合计及口径说明 |

退货订单是从真实订单复制的子集，**不能从真实订单移走**，否则出库与退货统计会失真。没有退货时保留表头。保留订单号、原始状态、物流、数量等所有字段；额外核对字段确有需要时追加在末尾，不覆盖源字段。

统计页主表保持简洁，数量为数值，订单号和 SKU 为文本。保留真实订单内实物 SKU 的零出库行。说明数据范围、物流判断、退货申请口径、非实物排除和跨月情况。业务口径尚有未决事项时，在结果旁明确标注暂定及影响数量，不把未知值表示为零。

优先使用关联真实订单的可读公式；源购买数量若为文本，确保公式实际能累计数值文本。需要状态分类或退货件数确认时使用显式映射/确认值，不把人工判断隐藏在模糊公式中。

公式与分拣表的更新能力不同：增删源记录、修改补单号或更改分类后，须重新分拣并刷新 SKU 列表与退货明细，不能宣称只靠统计公式就会自动更新全部工作表。若输出是静态快照，明确注明需重跑刷新。

## 校验和交付

保存前完成以下业务校验，而不仅是公式错误扫描：

1. 全量记录数 = 真实记录数 + 补单记录数；按源行身份核对互斥和覆盖，不依赖订单号唯一。
2. 分拣前后完整行多重集合一致；未重复、未漏行，非实物仍留在明细。
3. 退货订单是符合口径的真实订单子集，无补单、无未出库、无非实物。
4. 按同一 SKU 和确认退货件数，退货明细汇总 = 统计退货量；每个 SKU 净销量 = 出库量 - 退货量。
5. 用独立计算复算 SKU 与总计；缺码实物单列，不能漏出实物总数；数量按件数，不按行数。
6. 检查源行数据和原有格式、长订单号精度、编码替换及无关 sheet 保留情况。渲染检查新增表头、说明、数值和列宽；保存后重新打开验证。

完成时给出文件、实际生成的 sheet、出库/退货/净销量、补单匹配与未匹配数量。集中列出未决问题及下一步需要的资料，引导用户用退货订单与仓库的退回签收、入库记录核对。没有仓库回传数据时不宣称账实一致。

遇到异常时自动修正可确定的格式问题并告知；集中询问业务歧义；只暂停受影响部分，继续其他检查。不要反复询问已确认规则，也不要因等待期间没有回复就当作用户同意。

维护或大幅修改此技能时，用 [验收场景](references/acceptance-cases.md) 检查业务行为。
