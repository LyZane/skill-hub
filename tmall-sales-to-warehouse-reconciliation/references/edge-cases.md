# 重复运行与异常处理

## 重复运行

- 已有可靠“全量订单”：以其为完整来源，按本次补单号与编码映射重建派生表，不把已有补单行再次追加。
- 只有“真实订单”或已剔除补单的 export：不能将其静默改名为全量。检查是否有互补的旧补单表、会话中是否已有明确分拣记录。只有完整性得到证实时才可合并恢复；否则请求原始全量文件。
- 只有旧 export 与“补单”：若已知两表由同一全量互斥分拣而来，可以恢复全量。原始行序若无法恢复，明确说明；不能仅靠订单号去重拼表。
- 已有派生表且含用户新加的入库日期、退货运单或人工备注：先识别这些信息，按可靠行身份保留；关联键不唯一时请用户确认。不得删除人工核对成果再称重跑完成。
- 用户已明确授权刷新，且派生表没有额外人工数据时，说明将重建的范围后直接执行，不重复索要确认。
- 同名 sheet 若是其他用途，或目标文件已存在且来源不清，先解决命名/覆盖范围；不能默默用“统计2”制造两个权威版本。
- 原始备份与交付版本清楚区分，避免多个无说明的最终文件。保留全量不是保留原始未改编码的替代品：编码修改前需要可恢复原版。

## 退款与数量例外

退货属于约定的仓库对账业务口径，不是所有平台状态天然统一的事实。先读取出现的状态，再应用映射。

| 情形 | 操作 |
|---|---|
| 已出库、卖家同意退款等待退货 | 纳入，不要求交易关闭或退款成功 |
| 已出库、退款成功，整单退款且无相反证据 | 按购买数量计入 |
| 无物流、退款成功 | 不计出库和退货 |
| 已出库、退款申请处理中 | 默认按申请口径纳入；展示状态映射 |
| 已撤销/被拒绝/退款关闭 | 集中请用户确认是否仍按“曾申请”纳入；已确认的会话规则优先 |
| 已出库、退款状态空白 | 无法证明无申请；提示待核对，不静默归零 |
| 一单多件且部分退货 | 使用明确的退货件数；缺少件数则询问，不从金额反推 |
| 部分退款、差价补偿、仅退款不退货 | 提示与仓库实物退回不同，请用户确定是否沿用整行申请口径或排除/调整件数 |
| 有退货申请但无物流 | 默认不计出库和退货；如有线下发货证据，请用户补充物流或确认例外 |

用户确认例外后，用明确的订单/子订单/源行、调整件数、判定及依据记录，确保可复现。调整件数超过购买数量、为负或无法分配到商品行时不得直接采用。

如果用户明确要“所有申请过退款，包括撤销和拒绝”，遵循该口径，但统计旁注明，不能声称全部需退回仓库。若另有仓库已入库退货数，应作为不同指标，不能替换申请口径列而不告知。

## 物流、SKU 与订单号

- 物流公司有值但运单号为空：默认仍计出库，并报告这种组合；用户选择更严格口径时调整。
- 物流列缺失不同于单元格为空，先找语义一致的替代字段或请求重新导出。
- 发货时间有值但两项物流为空：不计；运费虚拟发货常有这种情况。
- 商品标题含“包邮”“支持退货”“补发”不等于非实物。明确的运费/补差商品才排除。
- 已出库的无编码实物保留待核对数量和来源；不根据另一个类似标题猜码。
- 一个主订单有多条明细：全部匹配；输入同时包含其主单号和子单号：每条明细只分配一次。
- 订单号匹配为全文精确相等，不使用子串、末几位或近似匹配。可以给出可疑差异供用户检查，但不能替用户认定。
- 不把来源不同但数值相同的订单号认定为重复行。合并多文件时需确认期间和覆盖重叠。

## 用户沟通示例

“46 个补单号匹配到 33 条明细，另有 13 个未匹配。我会先分拣已匹配部分，并列出未匹配号码供你核对来源。”

“发现 2 条退款已撤销订单，涉及 3 件。默认的申请口径可能与实际退回仓库不一致，请确认这部分按曾申请退款计入，还是排除。”

“这条记录购买 3 件，但备注表示只退 1 件。我会以你确认的退货件数为准；金额不足以可靠推算件数。”

“当前文件只有已剔除补单的真实订单，无法据此恢复完整的全量订单。请提供原始导出或对应的补单记录；我可以先检查现有记录的字段和物流状态。”
